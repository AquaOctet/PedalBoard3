## Decisions already made

These aren't obvious from the code. Each milestone's design decisions are in its plan under `docs/plans/` (the KD sections).

- **Releases are made by hand, from main only.** A maintainer starts a pipeline on main and clicks the release jobs. `release:gitlab` creates the tag `v<version>` and the Release. Nothing releases from a merge request or a pushed tag (!102).
- **Windows packaging.** An Inno Setup installer plus a portable zip, both unsigned for the beta (#40). Where things go:

  | What | Where |
  |---|---|
  | The app | `C:\Program Files\Pedalboard 3` |
  | Shared data | `C:\ProgramData\Pedalboard3`: created by the installer, not used yet (#93) |
  | Settings | `%APPDATA%\Pedalboard 3` |
  | Boards | `Documents\Pedalboard 3\Patches` |
  | Recordings | `Documents\Pedalboard 3\Recordings` |

  The installer's AppId in `installer/windows/Pedalboard3.iss` is permanent: upgrades find the installed copy by it.
- **Release builds link the MSVC runtime statically**, so no VC++ Redistributable is needed. `tools/package.ps1` checks this with dumpbin.
- **The version** is the numeric `project(VERSION)` plus `PB3_VERSION_SUFFIX` in `app-v3/CMakeLists.txt`.
- **Who publishes it.** The software is by **OpenZephyr LLC**, which is the company name in the exe and the
  installer's publisher. **AquaOctet** is the GitHub account and the personal site, so the About window
  credits aquaOctet at OpenZephyr LLC and links both (maintainer, 2026-10-13).
- **About** uses the wording the maintainer gave (!103). Every address is a constant at the top of `app-v3/src/ui/AboutWindow.cpp`.
- **Menus.** File holds files and About only. Settings holds the settings windows, App Mappings and Test Tone. The patch bank shows and hides from the bank itself, and from Window > Patch Bank on macOS.
- **Where the work lives.** GitLab (`void-realm-solutions/pedalboard-3`) is where it happens: issues, MRs and CI. `github.com/AquaOctet/PedalBoard3` is a push mirror of the protected branches.

## Known limitations and loose ends

- **Pipeline jobs never run.** `release:linux`, `release:macos` and `release:gitlab` have never run. The first pipeline started by hand on main is their first real run.
- **The last installer build.** `release:windows` ran once, on !99's pipeline (job 16476358836, artifacts kept until about 2026-09-28). All 579 tests passed, the runtime check passed, and it built the installer and the zip. Nobody has run that installer on a clean PC yet (#87).
- **Windows version info.** A file's Properties show version 1.0.0; the app and the installer show 1.0.0-beta.1 (#93).
- **dcomp.dll.** The CI-built Windows exe delay-loads `dcomp.dll`, a side effect of the Windows runner's JUCE patch. It's harmless on desktop Windows.
- **CLAP** defaults to ON without a preset, and its packages track `main` (#93).
- **Windows CI time.** The Windows job takes 20 to 35 minutes. A `release:windows` run with a cold cache took 58.

## Setting up the Mac

### Tools

```bash
xcode-select --install                          # Apple's compilers
brew install cmake ninja just pkg-config glab
```

CI's `lint:format` job uses the Linux image's clang-format 18, and other versions format a few constructs differently. To match it locally, `brew install llvm@18` and put `$(brew --prefix llvm@18)/bin` first on your PATH for `just format` and `just format-check`. Otherwise let CI's lint job be the judge.

### The repo

```bash
git clone git@gitlab.com:void-realm-solutions/pedalboard-3.git
cd pedalboard-3
just build        # the first configure downloads JUCE and the other dependencies
just test
just run
```

To render the UI snapshots on a Mac, run the tool you just built:

```bash
build/macos-dev/src/pb3-ui-snapshots_artefacts/Debug/pb3-ui-snapshots build/ui-snapshots
```

### GitLab

Run `glab auth login` (gitlab.com, SSH). The MR and issue scripts all go through glab.

### Claude Code

1. **The silkops-harness plugin** provides `ship-mr`, `watch-pipeline`, `milestone-from-plan` and the `ops/` scripts.
   - Clone `git@gitlab.com:void-realm-solutions/silkops-harness.git`, for example to `~/dev/silkops-harness`.
   - In Claude Code, run `/plugin marketplace add ~/dev/silkops-harness`, then `/plugin install silkops-harness@silkops`.
   - The scripts are in `~/dev/silkops-harness/ops/`.
2. **Optional: the compound-engineering plugin** gives the planning skills (`ce-plan` and others) behind `docs/plans/`. Install it with `/plugin marketplace add EveryInc/compound-engineering-plugin`, then install `compound-engineering`.
3. **No local silkOps settings token is needed.** The pipeline carries it.
4. **Start the first session** with something like: "Read AGENTS.md and docs/status/2026-09-14-handoff.md, then start on the macOS section of #87."

## How we work, in short

The full list is in [AGENTS.md](../../AGENTS.md#working-agreement). The essentials:
- File (or find) the issue first, and put `Closes #N` in the MR's first description.
- Ship through `ship-mr`.
- Report every CI job, the allowed-to-fail ones included.
- A human merges and releases.
